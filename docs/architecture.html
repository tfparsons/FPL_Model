FPL Model · system reference

Information architecture

How the FPL Model moves data and makes its decisions — every pipeline drawn, every rule of thumb written down with the number it uses. For reading alongside the code in src/mudchute/.

Matches the repo as of 1 Sep 2026 (GW3 of 2026/27 · model v1.5). Files in data/processed/ are committed so any run is reproducible from the repo alone.

1System map

Four principles shape everything: the xP matrix is the only contract between model and solver; every raw pull is a timestamped snapshot so a run can be replayed; the repo is the database — there is no server, the scheduler commits its outputs and Vercel serves static files; and the model is versioned — every run is stamped, so its recommendations can be audited against the exact rules that produced them.

2Data layer

Pulled every update
bootstrap-static (600 players: season totals, xG/xA, status, price projections), fixtures (380, with kickoff and GW), entry/{team_id}, …/history (chips), …/transfers, and the picks for the latest started GW. Each goes to data/raw/<UTC stamp>/; data/raw/LATEST points at the newest; the last 10 snapshots are kept.
Pulled once
vaastav's 2025-26 and 2024-25 season CSVs (fixtures, teams, players_raw, merged_gw) into data/history/. Players are joined across seasons on the stable FPL code, never the per-season id.
Selling prices
Replayed from the transfers endpoint: purchase price = cost at the transfer that brought the player in, or season-start price if owned since GW1; sell = purchase + ⌊profit / 2⌋ in £0.1m units. The API won't reveal this without login, so it's reconstructed.
Free transfers
Not exposed unauthenticated, so the ledger is replayed from the actual transfer history: 1 FT ahead of GW2, each deadline consumes what was used (wildcard and free-hit weeks consume nothing) and banks +1, capped at the limit the API's game settings declare. Ignore a recommendation and the count still comes out right.
Confirmed transfers
The public API hides transfers made mid-window until the deadline passes, so moves already made are declared in config/confirmed.yaml (one line per transfer). The loader applies them to the squad, bank, selling prices and FT count before anything else runs — confirmed beats suggested, everywhere. Entries for past gameweeks are ignored once the API catches up.
Politeness
Browser-style User-Agent, 0.5s between calls, three retries with backoff. The live-points endpoint for a finished GW is cached permanently because it never changes.

3xP engine

3a · Minutes model minutes.py

The load-bearing component. Three quantities per player per fixture:

avail       = 1.0 (a) · chance/100 (d, default 0.75) · chance/100 or 0.1 (i) · 0 (s, u)
prior       = ½·late-season start rate + ½·full-season start rate   (last season)
              fallback: price prior (≥7.0m → 0.78, ≥5.5m → 0.60, ≥4.8m → 0.45, else 0.30)
              floor 0.90 if price ≥ 10.0m, fit, and ≥2000 mins last season
w           = n / (n + 1.5)          n = this season's games the club has played (the prior fades all season)
p_start     = avail · clip(w · evidence + (1 − w) · prior, 0, 0.97)      evidence = 0.7 · last-6 window + 0.3 · season rate
p_appear    = avail · (base + (1 − base) · sub_prob)      sub_prob from last season, default 0.15
p60         = p_start · P(60+ | start)                   last season, default 0.85 (GK 0.99)
mins_per_start = (s · window + 5 · last season) / (s + 5)      s = starts in the last-6 window (decay-weighted minutes)
xmins       = p_start · mins_per_start + (p_appear − p_start) · 18
Why flags are multipliers, not filters

A 75%-flagged player keeps 75% of his xP. The solver then weighs him against the alternatives instead of the model pre-deciding. Never hard-drop.

Knock-on: minutes belong to slots

Each club starts ~N per position (its formation shape from the game logs, blended with last season). Candidates' standalone P(start) should sum to the slots. A known absence (availability ≤ 0.25) of a would-be starter (P(start) ≥ 0.4) that leaves a gap > 0.25 passes the shortfall to fit teammates in proportion to P(start) × headroom, blended 50/50 with learned pairings (who started when he was out, once 5+ such games exist); a slot no candidate can fill spills FWD→MID, DEF→MID, MID→FWD. An oversubscribed group (mass > slots + 0.5) scales down. Beneficiaries keep their own per-90 rates — knock-on moves minutes, never talent — and show as cover (orange, absentee named).

How much last season is there?

The prior's weight scales with last-season minutes — rel = min(mins_last / 1500, 1). Below that, the start-rate prior leans toward the price prior, this season's games weigh more (K slides from 1.5 to 1.0), substitution patterns blend toward defaults, and last-season rates are down-weighted by the same factor. Why: an injury-wrecked 700-minute season reads as "starts one game in five" otherwise, and two 90-minute starts can't overturn it. Under 750 minutes shows as thin (orange) until the club has played 4 games.

Recency: the last six games, not the season

Evidence for P(start) is the current club's last 6 games from per-player game logs (element-summary, cached per finished GW), weighted 0.8^age and blended 70/30 with the season rate — the blend scored Brier 0.163 vs 0.191 for season-to-date on last season's logs (VALIDATION.md). The rate is the window's; the confidence in it is the club's season game count, so last season's prior fades as games mount (it used to be frozen at the window length, leaving a backup-prior starter a fifth short all year) while form can still turn in six games. Minutes per start blend the window's starts with last season's pattern, last season worth five starts (both backtested on 2025-26, v1.12; VALIDATION.md). A regular who reappears after missing 3+ games is a returner: start probability capped at 0.75 and minutes trimmed 15% until 2 games of evidence. Both cases show orange in the dashboard.

Club moves: evidence earned elsewhere doesn't count

A mid-season mover (detected by diffing each player's club against the last committed matrix, tracked in club_moves.json) restarts from the price prior with only new-club games as evidence, weighted n / (n + 1.0) so two games settle it either way. Summer signings and players with no PL record get the same fast-learning weight. For all of them, until the club has played 4 games: rates from another club are half-weighted with a 300-minute prior, and the new club's attack uplift is capped at 1.0 — otherwise old-club volume × new-club firepower double-counts. The matrix flags these rows (adjusted) and the dashboard shows their xP in orange.

3b · Rate blending xp.build_rates

rate90 = (last · w_last + current · mins_cur + prior · 600) / (w_last + mins_cur + 600)
         w_last = min(mins_last, 3000) · 0.6      prior = position median of regulars (≥1200 mins)
         prior  = position 80th percentile for players priced ≥ 8.0m     bonus uses 900 pseudo-mins
defcon_rate = (hits · apps60 + prior · 8) / (apps60 + 8)   hit = count ≥ 10 (DEF) or ≥ 12 (MID/FWD) in a 60+ min game
The defensive-contribution trap

In the historical data defensive_contribution is the raw action count (Caicedo: 12, 7, 23…), not the 2-point award. Treating it as points put defensive midfielders on 14 xP a week. The model estimates the probability of clearing the threshold instead.

3c · Team strengths & fixture λ strengths.py

att_home = 1 + 0.7 · (GF_home / L_home − 1)        (and att_away, def_home, def_away alike)
promoted side: att 0.80, def 1.20     blend toward this season: w = n / (n + 10)
λ_home = L_home · att_home[h] · def_away[a]         λ_away = L_away · att_away[a] · def_home[h]
att_mult = λ_for / team baseline goals              conc_mult = λ_against / team baseline conceded

FPL's own strength ratings are zeroed at the start of a season, so strengths come from last season's goal rates (shrunk 30% toward average) and blend toward live results as games accumulate.

3d · Points per fixture xp.build_xp

share      = xmins / 90
appearance = p60 · 2 + (p_appear − p60) · 1
goals      = share · xG90 · att_mult · {{GK 10, DEF 6, MID 5, FWD 4}}
assists    = share · xA90 · att_mult · 3
cs         = p60 · e^(−λ_against) · {{GK 4, DEF 4, MID 1}}
gc         = − share · E[⌊k/2⌋],  k ~ Poisson(λ_against)      (GK, DEF)
saves      = share · saves90 / 3 · conc_mult                    (GK)
defcon     = p60 · defcon_rate · 2                               (outfield)
bonus      = share · bonus90        cards = − share · yellow90
xP[GW]     = Σ over the team's fixtures in that GW

Output: xp_matrix.csv (one row per player, one column per GW in the horizon, plus minutes-model columns) and xp_components.csv (the nine components per player per GW, used for the "drivers" line in the report).

4Solver solver.py

Pool
Your 15 + the top 15 GK / 45 DEF / 55 MID / 30 FWD by 8-GW xP + the 6 cheapest likely starters per position (bench fodder). ~155 players, 8 GWs.
Decisions
Binary squad, lineup, captain, transfer_in, transfer_out per player per GW; integer ft, used_ft, paid, free_wc per GW; continuous bank. Vice-captain and bench order are chosen after solving — provably optimal given the squad/lineup split, and 6,000 fewer binaries.
Hard rules
15 players as 2-5-5-3; ≤3 per club; 11 starters with GK 1, DEF 3–5, MID 2–5, FWD 1–3; captain in lineup; ≤20 transfers per GW; bank ≥ 0 every GW.
Money
Buy at now_cost; sell at the reconstructed selling price for the players you own, at now_cost for anyone bought during the horizon. Prices are held static across the horizon.
Free transfers
used_ft + paid + free_wc = transfers, used_ft ≤ ft, ft[t+1] ≤ ft[t] − used_ft + 1, capped at the API-declared limit (currently 5). free_wc is only allowed in a wildcard week.
Objective
Σ_t 0.85^t · [ Σ_p xP·((1−w)·lineup + w·squad + captain) − 4·paid ] with bench weight w = 0.03 for the GK, 0.10 average for outfield (from 0.18 / 0.09 / 0.04 per slot) — plus the option-value terms below.
Option value
Three terms teach the solver that a spare transfer is worth something: FTs still banked at the horizon's edge earn terminal bonuses (2.3 / 2.1 / 1.7 decayed xP for the first three); planned future moves carry a tax of 1.75 decayed xP per transfer; and a small churn penalty (0.05 per change) breaks ties toward stability. All three were calibrated by simulation — two-stage experiments measuring what a banked transfer is actually worth when news breaks — and are settings, not hard-coded.
Chips
Wildcard, Bench Boost and Triple Captain are extra solves with the chip allowed once anywhere in the horizon; the gain vs baseline and the GW chosen are reported, never auto-played. Free Hit is approximated by a single-GW re-pick at current squad value. The verdicts come from chips.py: the chip calendar is read from the FPL data (two of each chip, one usable in each half, an unused first-half chip lost at GW19), so each chip carries a runway to its expiry. The xP bar it must clear slides linearly to zero as its pressure runway (weeks left minus the other unplayed chips that need a week of their own) closes. Each has its own trigger — bench boost: a fully fit 15 and a bench above its horizon norm, or the week after a wildcard; triple captain: the captain's week unusually high for him, or a double; free hit: a blank for a chunk of the starters or an injury crisis, otherwise held longest — and a double anywhere in the window, even beyond the solver's view, is held for. 'Would add' is in each chip's own units, undiscounted: the bench's points net of the autosub credit, one more captain multiple, the one-week re-pick gain; the wildcard is judged on what its rebuilt squad adds over the next five gameweeks from the week it is played. The chip solves' discounted deltas are kept as solver_gain but sit inside the solver's tolerance, so they are not the headline. Once the rest of the half is in view an endgame planner assigns each remaining chip a distinct week (one chip per gameweek), which also settles who gets a double.
Tolerances
Baseline: 0.2% gap, 120s. Chips: 0.5%, 60s. Robustness: 2%, 25s. HiGHS via highspy, no commercial solver.

5Checks & timing pipeline.py · robustness.py

Hit threshold
If the baseline took a hit, solve again with no_hits. Keep the hit only if it beats that plan by ≥ 2.0 decayed xP (hit_threshold in settings).
Move bar
A move must also beat doing nothing: the plan is re-solved with zero transfers, and the package is only recommended if it clears holding by 1.75 decayed xP per transfer spent — the simulated value of keeping the option open. The report shows the full decomposition (hold / best single / the package) so the decision rule is visible, not just its verdict.
Robustness
The shake test: re-solves with xP × exp(N(0, 0.15)) per player × exp(N(0, 0.08)) per player-GW. The first-GW transfer count is pinned to the adopted plan's — unpinned, noise makes hit-sprees look profitable and the runs answer the wrong question. Sampling is adaptive: 25 runs normally, escalating to 100 when the answer could actually change — conviction in the ambiguous 30–70% band, the gain within 1.0 of the bar, or inside the final 24h before the deadline. Reported: payload conviction (how often the key player is bought — for multi-transfer moves the exact pair rarely repeats under noise, so conviction is the honest headline), exact-set survival, per-player rates and the most common alternative moves.
Timing
Default: late — inside the final 24h before the deadline, stated in UK time, once team news is in. The report argues for early only when a recommended package is genuinely at risk: the plan is an exact fit for the budget (little slack), the prices involved are projected to move against it, and the fallback package costs ≥ 1.5 xP. The alert quantifies the risk — probability the package breaks tonight and by the deadline, from FPL's own price-change projections — and states the act-window: after the last involved player's fixture, before the nightly price change.
After transfers are made
Once transfers are made, the call card flips state: it shows the moves with the rationale captured from the run that recommended them (gain vs bar, price risk, conviction), matched against the run log — or marks them plainly as the manager's own call if they differ. The remaining advice re-frames around what's left: captaincy, line-up, and whether anything more is worth a hit.
Schedule awareness
Deadline, first/last kickoff, midweek (first kickoff Tue–Thu), doubles and blanks per GW, postponed fixtures (GW = null count as blanks), and a diff of fixture GWs/kickoffs against the previous snapshot — all from the fixture list, nothing assumes a Saturday.

6Scheduling & deployment

A run is due when
no plan exists yet · a GW has been finalised (data_checked) since the last run · inside the final 24h before a deadline with the last run ≥ 6h old · it's a new day past the morning anchor (~07:00 UK) · backstop: the last run is ≥ 24h old. The dashboard's ↻ Refresh button skips the question entirely — it dispatches the workflow via a small Vercel function.
What the Action commits
data/processed/ (plan, xP matrix, components, history, outcomes), report.html, site/. Raw snapshots stay local to the runner.
Vercel
Static project, outputDirectory: site, no build. Every push to main redeploys; the dashboard URL is stable. Manual runs: the Actions tab → Run workflow.
Known risk
FPL sometimes blocks datacentre IPs. If the update step starts failing in Actions, the fallback is a laptop-side make all — the same commit-and-push path.

7Track record history.py

Recorded per run
time, GW, model version, free transfers in hand, transfers in/out, hits, captain, vice, lineup, bench, per-player xP, predicted points (lineup xP + captain − hits), conviction, gain vs the move bar, price-break risk, and the runner-up moves from the shake test — the full decision context, frozen at the moment of the call.
Settled per GW
once data_checked is true: model points = live points of the scored call's lineup + captain − hits (no auto-subs); the team's actual points and transfers from the entry endpoints; whether the decision was in line with the call.
Shown
a points-per-GW chart (predicted / model actual / team actual), a decision record per settled gameweek, and the full run log with each run's model version.
Model versions
changelog.py is the single home for the model version and its changelog — every change to how the model scores or recommends bumps the version and adds an entry (expected impact included). Runs and outcomes are stamped with the version they ran under, so a changed recommendation between runs is attributable to a model change rather than new data, and the track record can measure each version's actual impact as gameweeks settle under it. Reporting and UI changes deliberately don't bump it.

9Known limits & what's next

Minutes recency
Current-season start rate is season-to-date, not a recent window. The backtest shows recency is the biggest missing signal (the form baseline beats the model on rank correlation across all players precisely because recent points encode who is fit and starting). Fix: per-player element-summary pulls and a last-6-GW window.
Availability history
The backtest can't see injury flags, so its all-player error overstates live error; among players who played, the model is the best ranker of the three. See VALIDATION.md.
Prices
Held static over the horizon; a player you own, sell and re-buy inside the plan is valued at his original selling price. Both are standard simplifications.
Free Hit
Approximated as a one-GW re-pick, not modelled inside the multi-period solve.
Captaincy ceiling
Decisions run on mean xP, which undervalues the premium captain's haul potential — a 6.8-mean Haaland has far more upside than a 6.8-mean midfield committee. Variance is unmodelled; the captaincy list is a mean ranking.
Non-PL fixtures
European and cup games aren't in the FPL fixture list, so 'no match before the deadline' only sees league games.
Phase 2 candidates
OpenFPL projections as a drop-in for the xP matrix (the contract makes this a one-file swap); a full-season rolling solver simulation against your 2025/26; bookmaker odds for team strengths.
